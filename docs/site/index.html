Visão Geral

O que é este sistema?

Plataforma backend para oficinas mecânicas gerenciarem seu fluxo operacional completo — do cadastro do solicitante até o fechamento da ordem de serviço.

👤

Solicitantes & Veículos

Cadastro de solicitantes com validação de documento (CPF/CNPJ) e vinculação de múltiplos veículos por solicitante.

📋

Ordens de Serviço

Criação e acompanhamento de OS com cálculo automático de total, associando serviços e peças consumidas.

🔩

Peças & Serviços

Catálogo de serviços e controle de estoque de peças com ajuste de quantidade e rastreabilidade.

🔐

Autenticação JWT

Endpoints protegidos via middleware JWT. Token gerado no login, validado em todas as rotas autenticadas.

Banco de Dados

Por que PostgreSQL?

A escolha do PostgreSQL não foi arbitrária — cada característica do sistema motivou um requisito que o Postgres atende nativamente.

🔒

ACID e integridade transacional

Uma Ordem de Serviço agrega serviços, peças e atualiza o estoque em uma única operação. Se qualquer parte falhar, a transação inteira é revertida. O modelo ACID do Postgres garante que nunca haverá OS criada com estoque inconsistente ou total calculado errado.

🔗

Relações entre entidades com integridade referencial

O domínio tem uma hierarquia clara: Requester → Vehicle → ServiceOrder → ServiceItem / PartItem. Chaves estrangeiras com ON DELETE RESTRICT impedem remoção de solicitantes com veículos ativos e de peças referenciadas em OS abertas, sem nenhuma lógica extra na aplicação.

🔍

Consultas por índice em campos de negócio

Buscas frequentes por CPF/CNPJ (requester_document) e placa de veículo beneficiam-se diretamente de índices B-tree do Postgres, com custo de leitura O(log n) independentemente do volume de registros.

📊

Maturidade, ecossistema e observabilidade

GORM tem suporte de primeira classe para Postgres. pgAdmin (incluído no Docker Compose) oferece inspeção visual do schema sem ferramentas extras. A combinação garante produtividade no desenvolvimento e facilidade de diagnóstico em produção.

📈

Escalabilidade vertical e horizontal

Para o volume esperado de uma oficina mecânica, Postgres em modo single-node é mais que suficiente. Se o volume crescer, read replicas e particionamento de tabela são recursos nativos — sem migração de tecnologia.

Arquitetura

Arquitetura Hexagonal

O domínio não depende de nada externo. Todas as dependências apontam para dentro — frameworks, banco de dados e transporte HTTP são detalhes de infraestrutura.

Inbound

Adapters HTTP — adapters/inbound/http/

Handlers Gin. Recebem a requisição HTTP, validam o payload, chamam o use case e mapeiam o resultado para status code + JSON. Um arquivo por operação (create.go, find_by_id.go…).

↓
Ports

Interfaces — ports/usecases.go · ports/repositories.go

Contratos puros em Go. Use cases e repositories existem apenas como interfaces aqui. Nenhuma implementação — só assinaturas. Isso permite trocar Gin por gRPC ou Postgres por outro banco sem tocar o domínio.

↓
Application

Use Cases — application/usecase/{entidade}/

Lógica de negócio. Cada struct tem um único método Execute. Dependem apenas de ports e entities — nunca de Gin, GORM ou Postgres.

↓
Domain

Entities & Errors — domain/entities/ · domain/errors/

Núcleo do sistema. Zero dependências externas. Construtores (NewRequester, NewVehicle…), invariantes de negócio e erros sentinela (ErrNotFound, ErrInvalidDocument…).

↑
Outbound

Adapters PostgreSQL — adapters/outbound/postgresql/

Implementações GORM dos repository interfaces. Models em model/ com métodos FromDomain e ToDomain para converter entre entidade de domínio e model de persistência.

Regra de dependência

O único lugar que conhece todas as camadas é o cmd/api/bootstrap/container.go — o container de DI. Ele instancia repositories → use cases → handlers nessa ordem, injetando as dependências via construtores. Nenhuma outra parte do código importa camadas de fora para dentro.

Estrutura

Organização do projeto

Cada pasta tem uma única responsabilidade. A estrutura espelha diretamente as camadas da arquitetura hexagonal. 

cmd/api/
  main.go                  — entrypoint: monta container e inicia servidor
  bootstrap/container.go   — DI: instancia repos → use cases → handlers
  routes/routes.go         — registra SetupRoutes de cada handler
  middleware/              — JWT auth, CORS

internal/
  domain/
    entities/              — Requester, Vehicle, Service, Part, ServiceOrder
    errors/                — erros sentinela (ErrNotFound, ErrConflict…)

  ports/
    repositories.go        — interfaces dos repositories (driven ports)
    usecases.go            — interfaces dos use cases (driving ports)

  application/usecase/
    requester/             — CreateRequester, GetRequester, ListRequesters…
    vehicle/               — CreateVehicle, GetVehicle…
    part/                  — CreatePart, AdjustStock…
    service/               — CreateService, UpdateService…
    service_order/         — CreateServiceOrder, UpdateStatus…

  adapters/
    inbound/http/
      requester/           — handler.go + create.go + find_by_id.go…
      vehicle/
      part/
      service/
      service_order/
    outbound/postgresql/
      requester_repository.go
      vehicle_repository.go
      model/               — pgmodels com FromDomain / ToDomain

docs/
  site/                    — esta landing page (servida na porta 8083)
  swagger.json             — gerado pelo swag init

Métricas

Endpoints de métricas

Endpoints dedicados para acompanhamento operacional da oficina, acessíveis via API autenticada.

⏱️

Tempo médio de execução de OS GET /service-orders/metrics/execution-time

Calcula a média global do intervalo entre a aprovação do orçamento (started_at) e a finalização do serviço (finished_at) em todas as ordens de serviço concluídas. Retorna 0 caso nenhuma OS tenha sido finalizada ainda. 

// Resposta
{
  "average_seconds": 14400,
  "average_human":   "4h0m0s"
}
📦

Ajuste de estoque de peças PATCH /parts/{id}/stock

Aplica um delta (positivo ou negativo) ao estoque de uma peça. Retorna 422 Unprocessable Entity se o resultado deixaria o estoque negativo (ErrInsufficientStock). 

// Corpo da requisição
{ "delta": -3 }   // remove 3 unidades do estoque
{ "delta":  5 }   // adiciona 5 unidades ao estoque
