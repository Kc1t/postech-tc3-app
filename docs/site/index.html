Introdução

Visão geral

O Workshop API é o back-end (MVP) de um sistema integrado para uma oficina mecânica de médio porte. Ele substitui o atual processo baseado em planilhas e anotações manuais por um fluxo digital que cobre desde o cadastro do solicitante até a entrega do veículo.

👤

Solicitantes & Veículos

Cadastro de solicitantes (PF/PJ) com validação de documento e múltiplos veículos por solicitante.

📋

Ordens de Serviço

Criação, acompanhamento e atualização de status com cálculo automático de orçamento.

🔩

Catálogo & Estoque

CRUD de serviços, peças e insumos com controle de estoque e ajustes positivos/negativos.

🔐

Autenticação JWT

Access + refresh token com rotação, roles (admin/client) e portal público de consulta de OS.

Arquitetura

Arquitetura Hexagonal

Embora o desafio permitisse arquitetura em camadas tradicional, optou-se pela arquitetura hexagonal (Ports & Adapters) dentro de um monolito. O domínio não depende de nada externo — frameworks, banco e transporte HTTP são detalhes de infraestrutura.

Inbound

Adapters HTTP — adapters/inbound/http/

Handlers Gin. Recebem a requisição, validam payload, chamam o use case e mapeiam o resultado para status HTTP. Um arquivo por operação (create.go, find_by_id.go…).

↓
Ports

Interfaces — ports/usecases.go · ports/repositories.go

Contratos puros em Go. Use cases e repositories existem aqui apenas como interfaces — nenhuma implementação.

↓
Application

Use Cases — application/usecase/{recurso}/

Lógica de negócio. Cada struct expõe um único método Execute e depende apenas de ports e entities.

↓
Domain

Entities & Errors — domain/entities/ · domain/errors/

Núcleo do sistema. Zero dependências externas. Construtores, invariantes de negócio e erros sentinela centralizados.

↑
Outbound

Adapters PostgreSQL — adapters/outbound/postgresql/

Implementações GORM dos repositórios. Models em model/ com FromDomain e ToDomain.

Regra de dependência: O único lugar que conhece todas as camadas é o cmd/api/bootstrap/container.go — o container de DI manual. Ele instancia repositories → use cases → handlers, injetando dependências via construtores.

Arquitetura

Banco de dados — por que PostgreSQL?

A escolha não foi arbitrária — cada característica do sistema motiva um requisito que o Postgres atende nativamente.

  • ACID e integridade transacional — Uma OS agrega serviços, peças e atualiza estoque numa única transação. Se qualquer parte falhar, tudo reverte.
  • Integridade referencial — A hierarquia Requester → Vehicle → ServiceOrder → ServiceItem / PartItem é garantida por chaves estrangeiras (ON DELETE RESTRICT) sem lógica extra na aplicação.
  • UUID nativo — gen_random_uuid() sem dependências externas.
  • JSONB — Permite armazenar Value Objects (serviços e peças vinculadas à OS) como JSON consultável.
  • Índices B-tree em campos de negócio — Buscas por CPF/CNPJ e placa têm custo O(log n) independente do volume.
  • Maturidade e ecossistema — Driver oficial Go (pgx), GORM, pgAdmin para inspeção visual.
  • Escalabilidade — Para o volume de uma oficina, single-node basta. Read replicas e particionamento são nativos se crescer.
Domínio

Bounded Contexts

O sistema foi modelado em quatro contextos delimitados:

Identidade & Acesso

Usuários, autenticação JWT, roles e refresh tokens.

Atendimento

Solicitantes (PF/PJ), veículos e seu vínculo.

Oficina / Execução

Ordens de serviço, status, orçamento e métricas.

Catálogo & Estoque

Serviços oferecidos, peças/insumos e controle de estoque.

Domínio

Ordem de Serviço — Máquina de Estados

Os estados da OS e suas transições são controlados pela própria entidade ServiceOrder, nunca pelo handler HTTP.

Recebida → Em diagnóstico → Aguardando aprovação → Em execução → Finalizada → Entregue

Transições inválidas retornam ErrInvalidStatusTransition e o handler traduz para 422 Unprocessable Entity.

Visão geral da API

API

Endpoints de métricas

GET
/api/v1/service-orders/metrics/execution-time

Calcula a média global do intervalo entre started_at (aprovação do orçamento) e finished_at (finalização) de todas as OSs concluídas. Retorna 0 caso nenhuma OS tenha sido finalizada.

{
  "average_seconds": 14400,
  "average_human":   "4h0m0s"
}
PATCH
/api/v1/parts/{id}/stock

Aplica delta (positivo ou negativo) ao estoque de uma peça. Retorna 422 com ErrInsufficientStock se o resultado deixaria o estoque negativo.

{ "delta": -3 }   // remove 3 unidades
{ "delta":  5 }   // adiciona 5 unidades
Segurança

Práticas aplicadas

  • JWT com access token (15 min) e refresh token (7 dias) com rotação;
  • bcrypt (custo 12) para hash de senhas;
  • Validação de dados sensíveis: CPF/CNPJ e placa de veículo validados no domínio;
  • Account lockout após N tentativas de login falhadas;
  • Limites de tamanho em todos os inputs;
  • Variáveis de ambiente para segredos (sem credenciais hardcoded);
  • Roles (admin, client) — rotas administrativas exigem role=admin.
